# 0001. Pizza DB를 분석 lifecycle의 source of truth로 사용

- 상태: Accepted
- 결정일: 2026-08-17

## 맥락

Pizza는 분석 요청과 초기 리포트를 DB에 저장한 뒤, 트랜잭션 커밋 이후 `AnalysisRequestCreatedEvent`를 처리해 프로세스 내부 `InMemoryAnalysisJobQueue`에 작업 ID를 넣습니다. 네 개의 worker thread가 작업을 꺼내 `RUNNING`으로 변경하고 분석 입력을 계산한 다음 Pickle의 SQS request queue로 전송합니다.

현재 구현은 애플리케이션 시작 시 DB의 모든 `RUNNING` 요청을 `QUEUED`로 되돌리고, 모든 `QUEUED` 요청을 인메모리 큐에 다시 넣습니다. 이 복구 동작은 단일 프로세스 재시작에는 도움이 되지만 다음 한계가 있습니다.

- 인메모리 큐의 항목은 프로세스 외부에서 관찰하거나 여러 인스턴스가 공유할 수 없습니다.
- DB 상태와 인메모리 큐 항목이 서로 다른 시점에 변경되어 둘을 원자적으로 유지할 수 없습니다.
- 현재 `RUNNING`은 Pickle 전달 완료가 아니라 Pizza worker의 처리 시작을 의미합니다.
- 재시작 시 모든 `RUNNING`을 즉시 재전송 대상으로 바꾸므로 아직 Pickle에서 처리 중인 작업과 중복될 수 있습니다.
- 재시도 횟수와 다음 시도 시각이 영속화되지 않아 제한된 재시도 정책을 적용하기 어렵습니다.

분석 요청의 상태를 인메모리 큐가 아닌 영속 데이터에서 복원하고, 재시도와 운영 관측의 기준을 하나로 통일할 필요가 있습니다.

## 결정

Pizza의 `analysis_request` 행을 Pizza가 소유하는 분석 lifecycle의 source of truth로 사용합니다.

- 분석 요청 생성과 초기 리포트 저장은 기존처럼 하나의 DB 트랜잭션에서 수행합니다.
- 인메모리 큐와 내부 worker를 제거하고, DB에서 전송 가능한 `QUEUED` 요청을 조회하는 Dispatcher로 교체합니다.
- Dispatcher의 재시도 횟수, 마지막 시도 시각과 다음 시도 가능 시각을 DB에 저장합니다.
- SQS request queue 전송에 성공한 요청은 `RUNNING`으로 전환합니다.
- `RUNNING`은 Pizza 내부 worker가 실행 중이라는 뜻이 아니라 Pickle에 전달되어 최종 결과를 기다리는 상태를 뜻합니다.
- 오래 머문 `QUEUED`와 `RUNNING` 요청은 상태, 시도 횟수와 기준 시각을 사용해 복구 대상을 판정합니다.
- 같은 요청이 다시 전달될 수 있으므로 `analysisRequestId`를 재전송과 중복 처리의 안정적인 식별자로 유지합니다.
- 기존 Box–Pizza API의 상태 이름과 응답 필드는 변경하지 않습니다.

구체적인 상태 의미와 전이 조건은 [분석 요청 lifecycle](../analysis-pipeline/lifecycle.md)에 정의합니다.

## 결과

### 이점

- 프로세스가 종료되어도 전송 대기 작업과 재시도 정보가 남습니다.
- DB 조회로 현재 적체량과 멈춘 작업을 확인할 수 있습니다.
- 동일한 영속 상태를 Dispatcher, 복구 작업과 운영 지표가 함께 사용할 수 있습니다.
- 후속 재시도와 멱등성 정책을 요청 ID와 저장된 시도 정보에 연결할 수 있습니다.

### 비용과 한계

- Dispatcher 조회, 상태 변경과 SQS 전송은 하나의 원자적 트랜잭션으로 묶이지 않습니다. 전송 후 DB 반영 실패 등 경계 장애에서는 중복 메시지가 발생할 수 있습니다.
- SQS 전달과 결과 소비 측에서 중복을 허용하고 멱등하게 처리해야 합니다.
- 이번 단계는 단일 Pizza Dispatcher를 전제로 합니다. 다중 인스턴스에서의 작업 선점 방식은 별도 결정과 구현이 필요합니다.
- 상태, 시도 횟수와 시간 정보를 저장하기 위한 schema 변경이 필요합니다.

### 후속 영향

- DB Dispatcher와 관련 schema는 후속 구현 PR에서 추가합니다.
- 재시도 횟수, backoff, 정체 작업 판정과 최종 실패 기준은 별도 실패 처리 명세로 구체화합니다.
- Pizza–Pickle 메시지의 중복 전달 처리 규칙은 메시지 계약과 멱등성 결정에 반영합니다.
